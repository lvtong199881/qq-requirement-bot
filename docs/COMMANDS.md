# 对话框里的指令

> 返回 [README](../README.md)

指令在 App 的需求对话框里发，跟普通发言一样，只是以 `/` 开头。
只有在需求跑起来之后才有意义——还没开始的需求，第一句话就是需求本身。

## 斜杠指令

| 指令 | 谁能用 | 作用 |
| --- | --- | --- |
| `/help` | 已授权成员 | 列出可用指令 |
| `/stop` | 已授权成员 | 打断当前正在跑的回合 |
| `/resume` | 已授权成员 | 上一轮异常中断时，从当前阶段接着跑 |
| `/release` | **只有系统管理员** | 释放当前会话与进程 |

`/release` 比「能驱动 bot」更严一档：它会把当前需求的工作目录、会话、
并发槽一起释放掉，普通成员点不到这个后果。

## 权限从哪来

权限只看用户表，不看你是谁拉进来的：

| 身份 | 能做什么 | 从哪来 |
| --- | --- | --- |
| 系统管理员 | 发起需求、通过/打回、管账号 | 第一个注册的账号自动是；之后由管理员在 App 的「账号管理」里改 |
| 普通成员 | 看需求、发言、看产物 | 自己注册就是 |

普通成员**看得见**「通过」「打回」两个按钮，但点了会被告知
「通过和打回只有系统管理员能操作」。这样做是有意的：藏掉按钮的话，
新人不知道这里该有人拍板，只会以为是自己漏看了什么。

## 说人话

不需要记指令，直接说：

| 说法 | 行为 |
| --- | --- |
| `通过` / `好的` / `可以` / `同意` / `ok` / `lgtm` | 放行当前阶段，进入下一阶段 |
| `打回：<原因>` / `不行` / `不对` / `有问题` / `重做` | 退回当前阶段重做 |
| `继续` / `接着跑` | 上一轮异常中断时，从当前阶段接着跑 |
| 其他任何内容 | 当作对当前等待事项的回答 |

流程由状态机驱动，所以 bot 永远知道自己在等什么：等澄清回答、等阶段确认、等合并确认。
你回什么，它按当前状态解释。

App 里的「通过」「打回」按钮也走同一条路——按下去等于发了 `通过`，
打回等于发了 `打回：<你写的原因>`。按钮只是替你打字，没有另一套协议。

## 消息有哪几种

1. **阶段开始**：`当前「设计」阶段中。`
2. **阶段完成 + 产物**：`设计阶段已完成。` + 产物（图片在消息里直接能看，文件点开能下载）
3. **等你确认**：把 agent 提出的疑点渲染成 A/B/C 选项，或一句「回复通过/打回」
4. **异常**：`阶段异常，请联系 bot 管理员，异常原因如下：…`
5. **完成**：`「<需求名称>」全部完成。`

agent 的工作过程不进对话框——过程文字只留在它自己的会话里，
你只会看到这几类状态和产物。

## 一个需求一个对话

做完之后这个对话还留着，能看到全过程。要开新需求就点「+」新建，
不要想着在旧对话里重新开始——那样会把两件事的进度混在一起。

旧数据（`.state/group-<id>.json`）仍然按原文件名存着，里面有需求进度、
当前阶段、返工次数。这个 `group-` 前缀和文件里的 `groupId` 字段是 QQ 时代的
历史命名，现在装的是 App 的 threadId；改名要动上百处、没有任何行为收益，
所以留名改语义。
