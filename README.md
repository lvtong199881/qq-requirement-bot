# qq-requirement-bot

![License](https://img.shields.io/badge/license-MIT-blue)

把需求全流程接到 QQ 群：在群里 @产品同学 说一句需求，它按「需求澄清 → 需求定稿 → 设计 → 技术方案 → 开发 → 代码评审 → 测试 → 验收 → 合并」自动跑，每个阶段产出后停下来等你回「通过」或「打回」。

```
你     @产品同学  欢迎弹窗的关闭按钮挪到右上角，整个弹窗改成官方 popup
产品同学  收到，开始处理：欢迎弹窗的关闭按钮挪到右上角
         当前「需求澄清」阶段中。
         需求澄清阶段已完成。
         产物：待提问清单.md
         等你确认：
         1. 关闭按钮是贴在卡片内侧还是骑在角上？
            A. 骑角，一半在卡片外（推荐）
            B. 完全在卡片内
你     @产品同学  A
产品同学  当前「需求定稿」阶段中。
         需求定稿阶段已完成。
         产物：PRD.md
         等你确认。
```

## 它怎么工作

```
QQ 群 → NapCat → WebSocket → bridge
                                ├─ 状态机：现在在哪一步、返工几次、在等谁
                                ├─ 任务包：角色卡 + 输入清单 + 硬约束 + 回执要求
                                ├─ 回合：每阶段一个 dsh，产出 _receipt-<阶段>.json
                                └─ 校验：产物在不在盘上、git diff 有没有东西
```

**bridge 持有流程，skill 只提供阶段能力。**

这是和早期版本最大的区别。以前把整份 skill 丢给一个 agent，让它自己判断「现在该干什么」，bridge 只能事后解析它吐出来的 `[[WAITING]]` 标记和产物文档来猜状态——状态列换个词、标记漏写、产物写错目录，群里的播报就变成错的，而根因极难定位。

现在阶段顺序、输入输出、产物校验、返工次数、停点全在 `src/flow.js` 的 `CHECKPOINTS` 表里，代码说了算。

| 阶段 | 角色 | 产出 |
| --- | --- | --- |
| 需求澄清 | 需求 agent | `待提问清单.md` |
| 需求定稿 | 需求 agent（同一会话） | `需求卡片.md`、`PRD.md` |
| 设计 | 设计 agent | `设计说明.md`、`figma-import/`、`design-images/` |
| 技术方案 | 方案 agent | `技术方案.md` |
| 开发 | 开发 agent | 源码、单元测试、debug 包；自己 commit + push |
| 代码评审 | 评审 agent | `代码评审报告.md`（阻断/应修/建议三级） |
| 测试 | 测试 agent（黑盒） | `测试报告.md`、截图 |
| 验收 | 验收 agent | `验收文档.md` |
| 合并 | 开发 agent | 合并回主分支并跑编译验证 |

评审发现问题会自动回开发修正、再复审，最多三轮。

## 关键设计

- **一个群 = 一个需求**。做完仍占着这个群，新需求要换群。
- **一个阶段 = 一个回合**。每回合只加载该阶段的角色卡（`skills/<角色>/SKILL.md`），上下文短、约束集中，比把整份 skill 塞进去可靠得多。
- **角色级会话复用**。需求澄清和定稿是同一个会话（agent 记得问过什么）；评审首审和复审也是同一个（记得提过什么问题）。
- **产物校验不信回执**。agent 在 `_receipt-<阶段>.json` 里声明做了什么，bridge 一律自己扫盘核对；开发阶段看 `git diff`（含已提交的），源码没法按文件名列。
- **状态只有一个真相源**。编排记录由 bridge 从状态机渲染，格式改版不影响任何逻辑。
- **零依赖**。Node 22+ 自带 `WebSocket` 和 `fetch`，`npm install` 都不用跑。

## 手动批准 vs 自动推进

`approval: "manual"`（默认）时每个阶段产出后停下等你；`"auto"` 时只有关键分叉、硬阻塞、不可逆动作才停。两种模式下「合并到主分支」都要你确认。

## 已知限制

1. **单 QQ 号只能有一个昵称和一个头像**。所以本方案是「一个 bot + 文字区分阶段」，做不到多个不同头像的角色 bot。要真多号需要多个 QQ 号 + 多个 NapCat 实例，且风控敞口成倍增加。
2. **NapCat 是非官方协议端**，有封号风险。请用小号，并保持 `maxMessagesPerMinute` 不要调高。
3. **回合之间进程重启**。shell 环境、临时变量不跨回合；进度靠状态机落盘的 `flow` 字段和产物文件续跑。
4. **设计阶段依赖 Figma MCP**。会话里没注入 `mcp__figma__*` 时，稿子只能出本地导入包，画布上没有 `fileKey`/`node-id`——不影响下游，但 Figma 里看不到。
5. **一个阶段一个回合，长阶段可能超时**。单回合默认 45 分钟，验收这种要逐条核对十几条标准的阶段可能逼近上限，必要时调 `turnTimeoutMs`。
