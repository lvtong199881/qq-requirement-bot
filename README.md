# qq-requirement-bot

![License](https://img.shields.io/badge/license-MIT-blue)

把需求全流程接进一个自带 App：建个群，进去说一句需求，它按「需求澄清 → 需求定稿 → 设计 → 技术方案 → 开发 → 代码评审 → 测试 → 验收 → 合并」自动跑，每个阶段产出后来问你一句：消息流里弹一张卡片，勾「通过」或「打回」（打回还能写理由）。

```
你    欢迎弹窗的关闭按钮挪到右上角，整个弹窗改成官方 popup
产品同学  收到，开始处理：欢迎弹窗的关闭按钮挪到右上角
         当前「需求澄清」阶段中。
         需求澄清阶段已完成。
         产物：待提问清单.md
         等你确认：
         1. 关闭按钮是贴在卡片内侧还是骑在角上？
            A. 骑角，一半在卡片外（推荐）
            B. 完全在卡片内
你    A
产品同学  当前「需求定稿」阶段中。
         需求定稿阶段已完成。
         产物：PRD.md
         等你确认。
```

它原本跑在 QQ 群里，现在 QQ 那套已经删掉了——手机 App 就是全部前端。

## 它怎么工作

```
Flutter App → /api/* → bridge
                        ├─ 状态机：现在在哪一步、返工几次、在等谁
                        ├─ 任务包：角色卡 + 输入清单 + 硬约束 + 回执要求
                        ├─ 回合：每阶段一个 dsh，产出 _receipt-<阶段>.json
                        └─ 校验：产物在不在盘上、git diff 有没有东西
```

**bridge 持有流程，skill 只提供阶段能力。**

这是和早期版本最大的区别。以前把整份 skill 丢给一个 agent，让它自己判断「现在该干什么」，bridge 只能事后解析它吐出来的 `[[WAITING]]` 标记和产物文档来猜状态——状态列换个词、标记漏写、产物写错目录，播报就变成错的，而根因极难定位。

现在阶段顺序、输入输出、产物校验、返工次数、停点全在 `src/flow.js` 的 `CHECKPOINTS` 表里，代码说了算。

| 阶段 | 角色 | 产出 |
| --- | --- | --- |
| 需求澄清 | 需求 agent | `待提问清单.md` |
| 需求定稿 | 需求 agent（同一会话） | `需求卡片.md`、`PRD.md` |
| 设计 | 设计 agent | `设计说明.md`、`figma-import/`、`design-images/` |
| 技术方案 | 方案 agent | `技术方案.md` |
| 开发 | 开发 agent | 源码、单元测试、debug 包；自己 commit + push |
| 代码评审 | 评审 agent | `代码评审报告.md`（阻断/应修/建议三级） |
| 测试 | 测试 agent（黑盒） | `测试报告.md`、截图 |
| 验收 | 验收 agent | `验收文档.md` |
| 合并 | 开发 agent | 合并回主分支并跑编译验证 |

评审发现问题会自动回开发修正、再复审，最多三轮。

## 关键设计

- **一个群 = 一个对话**。群里不 @ 需求 bot 就只是聊天；@ 一句它才开始跑需求，之后要继续跟它说也得 @——需求群里同时在聊别的事，不该全灌给 agent。做完仍留着能看到全过程。
- **IM 和需求引擎能分开部署**。IM 只有账号、群、消息，随便找台小机器甚至公网机器就能跑；引擎在自己那台能访问项目仓库、模拟器、模型凭证的机器上，反过来连 IM。详见 [部署分离](#im-与需求引擎分开部署)。
- **一个阶段 = 一个回合**。每回合只加载该阶段的角色卡（`skills/<角色>/SKILL.md`），上下文短、约束集中，比把整份 skill 塞进去可靠得多。
- **角色级会话复用**。需求澄清和定稿是同一个会话（agent 记得问过什么）；评审首审和复审也是同一个（记得提过什么问题）。
- **产物校验不信回执**。agent 在 `_receipt-<阶段>.json` 里声明做了什么，bridge 一律自己扫盘核对；开发阶段看 `git diff`（含已提交的），源码没法按文件名列。
- **状态只有一个真相源**。编排记录由 bridge 从状态机渲染，格式改版不影响任何逻辑。
- **零依赖**。Node 22+ 自带 `fetch`，`npm install` 都不用跑。App 侧也只有三个直接依赖。

## 账号与权限

- 用户名 + 密码注册，`scrypt` 存哈希，token 是 HMAC-SHA256 签的，7 天有效
- **第一次启动会建预设管理员** `admin` / `123456`，登录页上直接写着；登录后请改掉
- 之后注册的人都是普通成员，要提权由管理员在 App 的「账号管理」里改
- 管理员能建群、能 @ 需求 bot 提需求、在卡片上拍板、管别人账号；普通成员能看群、能聊天
- 普通成员**看得见**那张拍板卡片，提交才提示「只有系统管理员能操作」——藏起来反而让人以为是 bug
- 没有邮箱也没有找回密码，忘了让管理员在「账号管理」里重置

## 自带 App

`app/` 里是一个 Flutter 客户端：群列表、阶段进度、消息流、提问卡片、新建群、账号管理。

```bash
export PATH="$HOME/flutter/bin:$PATH"
cd app && flutter run -d macos
```

先起后端（`node src/index.js`），App 里的服务器地址填 `http://127.0.0.1:7881`
（手机填本机内网 IP）。公网访问走 Cloudflare Tunnel，不需要公网 IP、不需要备案
（详见 [配置说明](docs/CONFIG.md) 的「App API」一节）。
App 自己的说明在 [app/README.md](app/README.md)。

## IM 与需求引擎分开部署

单机一条命令就够（`node src/index.js`，IM 和引擎在同一个进程里）。想让「不做需求时也能在群里聊天」，可以把两边拆开：

| 进程 | 入口 | 干什么 | 需要什么 |
| --- | --- | --- | --- |
| IM | `node src/im.js` | 账号、群、消息、产物、App API | 只要 Node，不需要模型凭证和项目仓库 |
| 引擎 | `node src/engine.js` | 跑需求流程、spawn 回合、写代码 | 项目仓库、模型凭证、模拟器 |

引擎是「客户端」：它主动连 IM，用 HTTP 长轮询拿事件、回写消息和阶段。所以 IM 可以放在公网小机器上，引擎留在你开发那台 Mac 上，IM 不需要知道引擎在哪。

启动顺序：先起 `node src/im.js`，它会打印一次**引擎密钥**（也会存进 `.state/engine-token`）；把地址和密钥抄进引擎那台机器的配置：

```json
{ "im": { "url": "http://<IM 那台机器的地址>:7881", "token": "<引擎密钥>" } }
```

然后在那台机器 `node src/engine.js`。App 的群列表顶部会显示引擎在不在线——掉线时群照样能聊，只是 @ 了没人接。协议细节见 [API 参考](docs/API.md) 的「引擎通道」。

## 手动批准 vs 自动推进

`approval: "manual"`（默认）时每个阶段产出后停下等你；`"auto"` 时只有关键分叉、硬阻塞、不可逆动作才停。两种模式下「合并到主分支」都要你确认。

## 已知限制

1. **回合之间进程重启**。shell 环境、临时变量不跨回合；进度靠状态机落盘的 `flow` 字段和产物文件续跑。
2. **设计阶段依赖 Figma MCP**。会话里没注入 `mcp__figma__*` 时，稿子只能出本地导入包，画布上没有 `fileKey`/`node-id`——不影响下游，但 Figma 里看不到。
3. **一个阶段一个回合，长阶段可能超时**。超时按阶段配：开发 / 测试 / 验收默认 60 分钟，其余 30 分钟，面板「设置 → 阶段超时」可调。超时是中断不是重试，中断后发「继续」从当前阶段重跑。
4. **Mac 得常开**。bridge 要 spawn 回合、跑 git、读写本地目录，搬不到 Cloudflare Workers 上去。
5. **不强推消息**。App 靠轮询（列表 5 秒、详情 3 秒），不开着就收不到——这是刻意的，省掉推送服务那一整套。
